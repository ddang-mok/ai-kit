# 실제 프로젝트 아키텍처 시각화

## 언제 사용하는가
- README/데이터/알고리즘 분석 후, 코딩 전 전체 구조를 빠르게 이해해야 할 때
- 기존 코드를 읽고 현재 구현(As-is)과 제안 설계(To-be)를 구분해야 할 때
- 구현 중 API/DB/모델 연결 문제를 추적하거나 데모 전에 기술 구조를 설명할 때

## 입력
README 및 과제 규정, `AGENTS.md`, 현재 트리/실행 파일, 실제 import/API/데이터 파일, 앞 단계 분석 결과.

## 작업 순서 (기본은 읽기 전용)
1. 현재 작업 디렉터리의 실제 파일만 최소 범위로 확인한다. README, package.json/requirements, 앱 진입점, 라우트/서비스/데이터 로딩 코드를 우선한다. 대용량/비밀 파일은 열거나 출력하지 않는다.
2. 현재 존재하는 컴포넌트(As-is)와 구현 계획(To-be)을 별도로 나눈다. 존재하지 않는 DB·API·모델을 현재 구현으로 그리지 않는다.
3. 기술 스택은 탐색 근거가 있는 것만 명시하고, 프론트/백/AI/DB가 불필요하면 제거한다.
4. 가능한 범위에서 다음 다이어그램을 작성한다.
   - A. Mermaid `flowchart`: 컴포넌트/책임/통신 경로 (필수)
   - B. Mermaid `flowchart`: 데이터 입력→검증→처리→결과 (필수)
   - C. Mermaid `sequenceDiagram`: 사용자 행동→모듈 처리→응답 (동적 앱에만)
5. 그림 아래 실제 코드/근거 파일 경로 목록을 연결한다. 확인된 구성, 설계 제안, 미확인 가정을 표시한다.
6. 대회 제약/규모/시간을 고려해 단순화할 수 있는 모듈 1~3개와 P0 MVP 수직 흐름을 제안한다.
7. Mermaid 도식은 단순 문법으로 만든다. 큰 그림은 5~12개 노드 이하로 분할하고, 한글 노드 이름은 따옴표를 사용한다. Mermaid 이외에 텍스트로 구성요소와 연결도 요약한다.

## 출력 기본 형식
1. 프로젝트 현재 상황 2~4줄
2. 실제 구조(As-is) Mermaid + 각 노드의 실제 경로
3. 추천 구조(To-be) Mermaid + 제안 이유
4. 데이터 흐름 Mermaid + 입력·출력 스키마/검증 지점
5. 선택적 사용자 시퀀스 Mermaid
6. 파일/컴포넌트 → 기능 → 검증 항목 연결 표
7. 아직 확인이 필요한 사항 + 바로 착수할 구현 단위 1개

## 파일 저장 조건
- 기본은 대화창에 Mermaid 코드를 출력한다.
- 사용자가 명시적으로 파일 생성을 요청하면, 기존 파일을 덮어쓰지 않고 기본적으로 `docs/ARCHITECTURE.md`에 저장한다. 이미 파일이 있으면 내용을 먼저 확인하고 사용자 변경분을 보존한다.
- GitHub/VS Code의 Markdown에서 `mermaid` 코드블록을 미리보기로 확인할 수 있도록 한다. IDE 미리보기가 불가하면 코드블록/ASCII 간단 버전을 함께 제공한다.

## 금지
- 실제 코드·데이터를 읽지 않고 아키텍처를 단정하지 않는다.
- 분석 요청만으로 패키지 설치, 코드 변경, 원본 데이터 수정, 외부 API 호출을 하지 않는다.
- 인증정보/비밀 키/개인정보를 그림이나 로그에 포함하지 않는다.
- 제안 설계를 실제 구현처럼 보고하지 않는다.
